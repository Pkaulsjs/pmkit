LoopBack API Security Checklist

Written during live bug-bounty recon on a production fintech API (August 2026).

LoopBack's REST interface is powerful and equally dangerous when model ACLs are loose. A security review should walk this list before trusting any LoopBack backend.

The probes, in order

  1. Unauthenticated model access. For every model: GET /api/<model>?filter[limit]=1 with no token. A 200 here means missing ACLs - critical finding. A mature API returns 401 everywhere.
  2. Filter-injection IDOR. With any valid token: ?filter[where][id][neq]=<my-id>. If ownership filters are client-supplied, [neq], [inq] and friends read other tenants' rows.
  3. findOne abuse. /<model>/findOne?filter[where][...] bypasses list pagination rules; test every where-clause key for cross-tenant reads.
  4. Guest-token scoping. Apps that mint sessions pre-authentication must scope those tokens to zero sensitive models. Probe every endpoint with the guest token alone.
  5. Remote-method exposure. Custom methods (/<model>/<method>) often skip ACLs that the CRUD routes have. Enumerate them from the client bundle.

Hardening side

  • Deny-by-default ACLs; whitelist per-role per-model per-method.
  • Force server-side tenant predicates - never trust filter[where] ownership keys from clients.
  • Disable the explorer and verbose errors in production.
  • Scope refresh tokens to an explicit allowlist of models.

In our August 2026 scan of a production LoopBack deployment, all five probe classes came back properly denied - proof this checklist describes what mature teams actually defend. The client bundle alone exposed the full route map, which is why probe #0 starts at reading your own frontend.
