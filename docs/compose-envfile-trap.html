The env_file Parse-Time Trap

Found while shipping a Mastodon package to an app store; it survived local testing, passed CI, and would have broken every production install.

The pattern that fails

services:
  init:                      # one-shot: generates secrets
    command: generate-secrets --out /data/secrets.env
    volumes: [secrets:/secrets]
  web:
    depends_on:
      init:
        condition: service_completed_successfully
    env_file:                # reads secrets generated above?
      - /data/secrets.env    # NO.

It looks right: web starts after init completes. But compose resolves every service config - including env_file contents - at invocation start, not when each container is created. On first boot the file is empty or missing, so runtime containers get blank secrets forever. Local testing hides this because you usually re-run compose after the file already exists.

Three ways out

  1. Generate before compose runs - pre-start hooks or entry scripts write the file; compose parses after. Cleanest if your platform supports lifecycle hooks.
  2. All secrets from environment sourcing - deterministic derivation at env-load time (e.g., HMAC of a device seed per purpose), injected into compose interpolation. No files at all. Our choice where supported.
  3. Runtime self-configuration - containers read a mounted file themselves at boot and wait/reload. Works but adds wait-loop complexity to every service.

How to catch it

Clean-room test protocol: delete ALL state including the secrets file, run the exact install flow a fresh user sees, then assert the values landed in the runtime container (docker exec <svc> printenv KEY). If you only test restarts, you test the wrong boot.
